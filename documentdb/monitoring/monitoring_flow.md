# DocumentDB Monitoring Flow — From Postgres to Grafana

## Overview (One-Liner)

```
Postgres + Gateway  ──→  OTel Collector sidecar  ──→  Prometheus  ──→  Grafana
   (metric sources)       (collect, merge, expose)      (scrape, store)  (dashboards)
```

---

## The Full Chain (Step by Step)

### Step 1: Metric Sources (inside every database Pod)

Two components produce metrics inside the same Pod:

| Component | What it is | How it produces metrics |
|-----------|-----------|------------------------|
| **Postgres** | The actual database engine | Does nothing on its own — the OTel Collector runs SQL against it |
| **documentdb-gateway (PgMongo)** | MongoDB wire-protocol translator (Rust binary) | Pushes metrics via OTLP/gRPC to `localhost:4317` every 15 seconds |

### Step 2: OTel Collector Sidecar (the "metrics plumber")

A container injected into every database Pod by the operator (via CNPG sidecar-injector plugin).

**What it does (3 jobs):**

| Job | What happens |
|-----|-------------|
| **Receive** | Collects from 2 sources (see below) |
| **Process** | Memory limiting, batching, delta-to-cumulative conversion |
| **Export** | Exposes a Prometheus scrape endpoint at `:8888/metrics` (and optionally pushes to an external OTLP endpoint) |

**How it receives data from each source:**

| Source | Receiver Type | How it works | Frequency |
|--------|--------------|-------------|-----------|
| **Postgres** | `sqlquery` receiver | Runs SQL queries against local Postgres, turns row results into metrics | Every 30 seconds |
| **Gateway** | `otlp` receiver | Listens on `localhost:4317`, the gateway pushes OTLP metrics here via gRPC | Every 15 seconds (gateway push interval) |

**How it's configured:**

A Kubernetes ConfigMap named `<cluster>-otel-config` with two YAML files:

| File | Contains | Who creates it |
|------|---------|---------------|
| `static.yaml` | Receivers (sqlquery, otlp) and processors (memory_limiter, batch) | Embedded in the operator — add new SQL metrics here, no code change needed |
| `dynamic.yaml` | Resource attributes (cluster/namespace/pod labels), exporters (Prometheus port + optional OTLP), pipeline wiring | Auto-generated by the operator based on `spec.monitoring` |

### Step 3: Prometheus (the time-series database)

A standalone service that **scrapes** (HTTP GET) the `:8888/metrics` endpoint on each Pod.

| What it does | Detail |
|-------------|--------|
| Pulls metrics from | `:8888/metrics` on every database Pod |
| Stores | All metrics as time-series data (numbers + timestamps + labels) |
| Query language | PromQL |

### Step 4: Grafana (the dashboard visualizer)

| What it does | Detail |
|-------------|--------|
| Connects to | Prometheus as a data source |
| Queries | PromQL queries against stored metrics |
| Renders | Charts, graphs, gauges, tables — whatever dashboards you build |

## What Data is Collected — From Each Component

### A. From Postgres (via sqlquery receiver)

Collected by the OTel Collector running SQL queries every 30 seconds.

| Metric Name | Type | Description |
|------------|------|-------------|
| `documentdb.postgres.up` | Gauge | 1 = database is alive and responding to queries. Add more SQL queries in `base_config.yaml` — no Go code changes needed. |

> **How to add more:** Edit the SQL queries in the `sqlquery` receiver section of `base_config.yaml`. The operator embeds this file. Any `SELECT` that returns a numeric value can become a metric.

---

### B. From Gateway / PgMongo (via OTLP push)

Pushed by the gateway binary itself every 15 seconds to `localhost:4317`.
The operator **only enables** this by injecting two environment variables into the gateway container:

| Env Var | Value | Purpose |
|---------|-------|---------|
| `OTEL_METRICS_ENABLED` | `true` | Turns on the gateway's built-in OTLP metrics exporter |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | `http://127.0.0.1:4317` | Tells the gateway where to push metrics |

#### Request Metrics (8 counters — one per MongoDB operation)

Every metric carries these **labels (attributes):**

| Label | Example Value |
|-------|---------------|
| `db.system.name` | `"documentdb"` |
| `db.operation.name` | `"find"`, `"insert"`, `"update"`, `"delete"`, `"aggregate"` |
| `db.collection.name` | `"users"` |
| `db.namespace` | `"mydb"` |
| `error.type` | Error code string (only present on failed operations) |

| # | Metric Name | Type | Unit | Description |
|---|------------|------|------|-------------|
| 1 | `db.client.operation.duration.total` | Counter | seconds | Total time spent processing operations. Also emitted with an **extra label** `db.operation.phase` set to `postgres_begin_transaction`, `postgres_execution`, or `postgres_commit` — so you can see Postgres phase breakdown. |
| 2 | `db.client.operations` | Counter | count | Number of operations processed |
| 3 | `db.client.request.size.total` | Counter | bytes | Total size of incoming request payloads |
| 4 | `db.client.response.size.total` | Counter | bytes | Total size of outgoing response payloads |
| 5 | `db.client.documents.returned` | Counter | count | Documents returned (Find, Aggregate, GetMore only) |
| 6 | `db.client.documents.inserted` | Counter | count | Documents inserted (Insert only) |
| 7 | `db.client.documents.updated` | Counter | count | Documents updated (Update and FindAndModify only) |
| 8 | `db.client.documents.deleted` | Counter | count | Documents deleted (Delete only) |

#### Startup Metrics (2 — per gateway restart)

| # | Metric Name | Type | Unit | Description |
|---|------------|------|------|-------------|
| 9 | `gateway_startup_delay_ms` | Histogram | ms | Time from process start until gateway is ready to accept connections |
| 10 | `gateway.starts` | Counter | count | Number of times the gateway has reached ready state (restart counter) |

> **Important:** Counters use **delta temporality** — each push only contains the change since the last interval, not the cumulative total. The OTel Collector sidecar converts deltas into cumulative counters before exposing them to Prometheus.

## How the Operator Sets It All Up

Everything is driven by the `spec.monitoring` block on the DocumentDB custom resource:

```yaml
spec:
  monitoring:
    enabled: true
    exporter:
      prometheus:
        port: 8888        # default
      otlp:               # optional — push to external collector
        endpoint: "otel-collector.monitoring:4317"
```

| Operator Action | What it Does |
|----------------|-------------|
| **Reconcile OTel ConfigMap** | Creates/updates `<cluster>-otel-config` with `static.yaml` + `dynamic.yaml` |
| **Inject sidecar** (via CNPG plugin) | Adds the OTel Collector container + mounts the ConfigMap + injects gateway env vars |
| **Trigger rolling restart** | Annotates the CNPG Cluster when config changes, CNPG handles the pod rollout |
| **Cleanup** | Deletes the ConfigMap when `monitoring.enabled` is set to `false` |

## Quick Reference: Which Component Does What

| Component | Role | Runs where? | Talks to what? |
|-----------|------|------------|----------------|
| **Postgres** | Database engine — responds to SQL queries | Inside the DB Pod | OTel Collector (via SQL) |
| **Gateway (PgMongo)** | MongoDB protocol translator — pushes its own metrics | Inside the DB Pod | OTel Collector (OTLP → `localhost:4317`) |
| **OTel Collector sidecar** | Collects from Postgres + Gateway, processes, exposes | Inside the DB Pod (injected by operator) | Postgres (SQL), Gateway (OTLP), Prometheus (`:8888`) |
| **OTel ConfigMap** | Holds the Collector's YAML config | Kubernetes (mounted into Pod) | Mounted into OTel Collector at `/config/` |
| **DocumentDB Operator** | Creates ConfigMap, injects sidecar, handles cleanup | Kubernetes control plane | CNPG (for sidecar injection) |
| **CNPG** | Manages Postgres cluster lifecycle, handles rolling restarts | Kubernetes control plane | Database Pods |
| **Prometheus** | Scrapes and stores metrics | Separate deployment | OTel Collector (`:8888/metrics`) |
| **Grafana** | Queries Prometheus and renders dashboards | Separate deployment | Prometheus |
