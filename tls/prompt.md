## Reference facts (verify, don't trust blindly)

  `documentdb_gateway` process **inside the main `documentdb` container** (not a separate sidecar).
  Confirm in `documentdb/pkg/controllers/petset.go`.
- KubeDB postgres mounts TLS certs at **`/tls/certs`** (`PostgresSharedTlsVolumeMountPath` in
  `apimachinery/apis/kubedb/constants.go`). The gateway cert/key are expected under a **`gateway`
  subdirectory** → **`/tls/certs/gateway/tls.crt`** and **`/tls/certs/gateway/tls.key`**. Confirm the
  exact path convention by exploring `postgres/pkg` (how it builds cert volumes/mounts) and the
  `gateway` directory there.
- The DocumentDB API type currently has **no `spec.tls`** (confirm in
  `apimachinery/apis/kubedb/v1alpha2/documentdb_types.go`). That's why this test is manual.
- cert-manager is already a dependency across KubeDB; assume it is installed in-cluster (verify).
- Sample DB manifest: `documentdb/docdb.yaml` (kind `DocumentDB`, `kubedb.com/v1alpha2`, name `docdb`,
  namespace `demo`, 2 replicas).

## Definition of "the test passed"

All of these must be true:
- [ ] A cert-manager `Certificate` (certManager mode, our Issuer) produces a Secret with `tls.crt`
      and `tls.key`, whose SANs include the **gateway Service DNS names**.
- [ ] The gateway serves **TLS on 10260** using that cert.
- [ ] A MongoDB client verifies the cert against the **Service DNS name** it dials (no cert-name
      mismatch).
- [ ] A renewed/rotated cert is picked up by the gateway **without restarting the pod**
      (hot-reload) — OR you clearly document that a restart is required.
- [ ] The gateway → in-pod Postgres hop stays plaintext/loopback and backend replication TLS is
      untouched (you changed nothing there).

## Phase 2 — Provision the gateway cert (certManager mode)

Reproduce what the operator's cert reconciler will do:
1. Create a cert-manager **Issuer** (or reuse our org Issuer/ClusterIssuer) in the test namespace.
2. Create a cert-manager **Certificate** that:
   - targets a Secret (e.g. `docdb-gateway-cert-tls`) with keys `tls.crt`/`tls.key`,
   - `usages: [server auth]`, ~90d duration / ~15d renewBefore,
   - **`dnsNames` = the gateway Service DNS names** from Phase 0.
3. Wait for the Certificate `Ready`; confirm the Secret exists with both keys and inspect the cert
   SANs (`openssl x509 -in tls.crt -text -noout`) to prove the Service DNS names are present.

## Phase 3 — Wire the cert into the gateway MANUALLY (no operator code change)

Simulate the operator's mount + config step using `kubectl` only. Do **not** edit operator code —
patch the live workload (patch the `PetSet`/pod template, or clone the pod spec into a scratch
manifest in the test namespace). You must:
1. Add a **volume** from the cert Secret and **mount it read-only at `/tls/certs/gateway`** in the
   `documentdb` container (matching the postgres convention).
2. Configure the gateway to **use those files and enforce TLS**, using whatever mechanism Phase 0
   revealed (env `CERT_PATH=/tls/certs/gateway/tls.crt`, `KEY_FILE=/tls/certs/gateway/tls.key` +
   enforce flag, or the equivalent config/flags).
3. Let the pod roll; confirm the gateway process comes up pointing at the mounted cert (check logs /
   process args). If it falls back to a self-signed cert, the wiring is wrong — fix the path/args and
   note it.

> If the deployed image genuinely cannot be told to use a mounted cert without an operator code
> change, STOP and report exactly what's missing — that is the key finding.

## Phase 4 — Validate the TLS edge

1. `openssl s_client -connect <svc>:10260` → confirm a TLS handshake and that the presented cert is
   **our cert-manager cert** (matching serial/issuer), not a self-signed fallback.
2. Connect with a MongoDB client over **TLS** using the Service DNS name and our CA → confirm
   **verification succeeds** (no hostname/CA mismatch) and a query runs.
3. If enforce is on, confirm a **plaintext** client is now **rejected**.

## Phase 5 — Validate rotation (hot-reload)

1. Force renewal (shorten the Certificate duration/renewBefore, or trigger cert-manager to reissue)
   so the Secret's `tls.crt`/`tls.key` change.
2. Confirm the gateway **serves the new cert** (compare serials via `openssl s_client` before/after)
   **without a pod restart**, and existing connections aren't dropped.
3. If a restart is required, document that clearly — it changes the operator design.
