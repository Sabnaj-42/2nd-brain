# Gateway TLS — Live Test Results & Procedure (KubeDB DocumentDB)

**Date:** 2026-07-07
**Cluster:** k3s (`/home/sabnaj/k3s.yaml`), single node `sabnaj`
**Target:** DocumentDB `dcdb` in namespace `demo` (3 replicas, PetSet-managed, version `pg17-0.109.0`)
**Goal:** Prove gateway TLS works with an operator-provisioned cert, **without changing any code**
in the `documentdb` / `apimachinery` / `postgres` repos.

## Verdict

**PASS.** The gateway serves an externally-provisioned (certManager-style) cert, a MongoDB client
verifies it against our CA + the Service DNS name and authenticates over SCRAM, the cert
**hot-reloads on renewal without a pod restart**, plaintext is rejected, and the backend loopback is
untouched. It is safe to implement this in the operator by following the postgres cert pattern.

The whole thing was achieved with **zero code changes** — only a Kubernetes Secret + a `podTemplate`
passthrough on the DocumentDB CR.

## Key discoveries (ground truth from the running cluster)

| Fact                       | Finding                                                                                                                                                                                                                                                      |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Gateway runtime            | Upstream stack:`emulator_entrypoint.sh` → `build_and_start_gateway.sh` → `documentdb_gateway` binary, reading `pg_documentdb_gw/target/SetupConfiguration_temp.json`. Runs **inside the `documentdb` container** (not a separate sidecar). |

| Cert mount path convention | KubeDB postgres uses`/tls/certs` (`PostgresSharedTlsVolumeMountPath`). We mounted the gateway cert at **`/tls/certs/gateway/`** → `tls.crt`, `tls.key`, `ca.crt`.                                                                         |
| Workload control           | Pods owned by**PetSet** `dcdb` (`apps.k8s.appscode.com/v1`); reconciled by **`kubedb-kubedb-provisioner-0`**. Update strategy **`OnDelete`** → pods must be deleted manually to pick up template changes.                         |
| cert-manager               | Only**CRDs** are installed (`certificates`/`issuers.cert-manager.io`); the **controller is NOT running**. So certManager *mode* could not be exercised here directly — see "certManager note" below.                                      |

### The injection method (no code change)

Rather than editing the PetSet (which the provisioner reverts) or scaling the operator (shared-infra,
correctly disallowed), we injected the cert through the **DocumentDB CR `podTemplate` passthrough**.
The operator itself rendered it into the PetSet — testing the exact mechanism the operator will use:

```
spec.podTemplate.spec.volumes[]           += { name: gateway-tls, secret: dcdb-gateway-cert-tls }
spec.podTemplate.spec.containers[documentdb].volumeMounts[] += { gateway-tls -> /tls/certs/gateway (ro) }
spec.podTemplate.spec.containers[documentdb].env[]          += CERT_PATH=/tls/certs/gateway/tls.crt
                                                              KEY_FILE=/tls/certs/gateway/tls.key
```

## Procedure (reproducible)

All commands assume `export KUBECONFIG=/home/sabnaj/k3s.yaml`.

### 1. Generate a CA + gateway server cert with the Service SANs

(represents exactly what cert-manager issues in `certManager` mode)

```bash
openssl genrsa -out ca.key 2048
openssl req -x509 -new -nodes -key ca.key -sha256 -days 3650 \
  -subj "/CN=documentdb-gateway-test-ca" -out ca.crt
openssl genrsa -out tls.key 2048
# san.cnf: CN=dcdb.demo.svc, SANs = dcdb, dcdb.demo, dcdb.demo.svc,
#          dcdb.demo.svc.cluster.local, localhost, dcdb-pods, *.dcdb-pods.demo.svc.cluster.local
openssl req -new -key tls.key -subj "/CN=dcdb.demo.svc" -out tls.csr -config san.cnf
openssl x509 -req -in tls.csr -CA ca.crt -CAkey ca.key -CAcreateserial -days 90 \
  -sha256 -extensions v3_req -extfile san.cnf -out tls.crt
```

### 2. Create the Secret (the operator/cert-manager end-state)

```bash
kubectl create secret generic dcdb-gateway-cert-tls -n demo \
  --from-file=tls.crt --from-file=tls.key --from-file=ca.crt
```

### 3. Inject via the DocumentDB CR podTemplate (no code change)

```bash
kubectl patch documentdb dcdb -n demo --type=json -p '[
 {"op":"add","path":"/spec/podTemplate/spec/volumes","value":[{"name":"gateway-tls","secret":{"secretName":"dcdb-gateway-cert-tls"}}]},
 {"op":"add","path":"/spec/podTemplate/spec/containers/0/volumeMounts","value":[{"name":"gateway-tls","mountPath":"/tls/certs/gateway","readOnly":true}]},
 {"op":"add","path":"/spec/podTemplate/spec/containers/0/env","value":[{"name":"CERT_PATH","value":"/tls/certs/gateway/tls.crt"},{"name":"KEY_FILE","value":"/tls/certs/gateway/tls.key"}]}
]'
```

### 4. Roll pods (OnDelete) to apply

```bash
kubectl delete pod dcdb-0 -n demo   # repeat per pod; roll standbys first, primary last
```

## Known issue observed (NOT a TLS problem) — dcdb-1 stuck in standby recovery

Rolling the **primary** (`dcdb-2`) triggered an HA failover to `dcdb-0`. Afterward, `dcdb-1` fell
into a **persistent standby-recovery loop** (not merely slow): its Postgres is stuck
`the database system is starting up`, **waiting for WAL** (`contrecord requested by 0/1E000028`,
`waiting for WAL to become available at 0/1E000040`), while the coordinator repeatedly tries to run
it as a follower and fails the `pg_rewind` check because the local server never finishes starting:

```
on_Leader_change: Trying to run as follower... check if pg rewind need or reinitialization need
ha_postgres: Failed on primary changed ... pq: the database system is starting up (57P03)   # loops
postgres:    FATAL: the database system is starting up                                       # loops
```

Because `build_and_start_gateway.sh` waits for local Postgres before launching the gateway,
**dcdb-1's gateway stays down** — its config is already `PemFile`, so it *would* serve our cert once
Postgres recovers.

**Honest assessment:**

- This is a **Postgres/replication (HA)** matter, **orthogonal to TLS**. The gateway config on
  dcdb-1 is correct (`PemFile`); only its local Postgres is unhealthy.
- The DocumentDB was already in **`Critical`** status *before* any TLS change (pre-existing fragility).
- **I triggered the failover** by rolling the primary during the test, which tipped dcdb-1 into this
  loop. It had not self-resolved ~10 min later.
- `dcdb-0` (primary) and `dcdb-2` (standby) are healthy and serve TLS correctly throughout — the
  client TLS edge via the Service works.

**Remediation (Postgres, not TLS — needs a decision):** typical KubeDB fixes are to let it
reinitialize, or force a fresh basebackup by deleting dcdb-1's PVC + pod (destructive to that
replica's data only). Not done here without approval. On a healthy cluster, roll standbys first and
the primary last, waiting for full Ready + `pg_isready` between each, to avoid this.

## certManager note (why the Secret was created manually here)

Our org uses `gateway.mode: certManager`. In this cluster only the cert-manager **CRDs** are present;
the **controller is not running**, so a `Certificate` object would never be fulfilled. The Secret we
created by hand is **byte-for-byte the end-state** cert-manager produces in certManager mode
(`tls.crt` / `tls.key` [+ `ca.crt`]). Because the gateway only consumes the *files*, the gateway side
is identical regardless of who issued them.

To exercise real certManager mode later:

1. Install the cert-manager **controller** (CRDs already present).
2. Create an `Issuer`/`ClusterIssuer` (our org CA).
3. Create a `Certificate` with `dnsNames` = the gateway Service DNS names, targeting Secret
   `dcdb-gateway-cert-tls` — the operator's cert reconciler will create this object.
4. Everything downstream (mount + env + enforce + hot-reload) is exactly as tested above.

## What the operator must implement (validated blueprint)

1. **Cert reconciler** (certManager mode): create a cert-manager `Certificate` (issuerRef = our
   Issuer) with SANs = the gateway Service DNS names → Secret with `tls.crt`/`tls.key`; set
   `status.tls.{ready,secretName}`.
2. **Gate on `status.tls.ready`**, then in the rendered PetSet for the `documentdb` container:
   - mount the Secret **read-only at `/tls/certs/gateway`**,
   - set env **`CERT_PATH=/tls/certs/gateway/tls.crt`**, **`KEY_FILE=/tls/certs/gateway/tls.key`**.
3. Nothing else — the upstream gateway image handles PemFile loading, enforce-by-default, and ~60s
   hot-reload automatically. Follow the postgres repo's cert-volume/mount plumbing for the code shape.
